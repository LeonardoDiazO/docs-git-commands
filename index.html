Changes since Git for Windows v2.55.0(5) (August 20th 2026)

Following the MSYS2 project, on which Git for Windows is based, Windows 8.1 support was dropped; In doing so, internal paths changed (/mingw64/bin/git.exe does not exist anymore, /ucrt64/bin/git.exe takes its role; if this breaks your setups, consider switching to /cmd/git.exe instead, which is guaranteed to stay stable).

An issue with the installer for the previous version (v2.55.0.windows.5) caused the "Use external OpenSSH" option to be disabled for some users. This caused the bundled version of OpenSSH to be installed and overwrote any previously-saved choice of external OpenSSH. If you rely on an external OpenSSH installation, and you updated to v2.55.0(5), you should consider re-running the latest installer with "Only show new options" unchecked so that you can re-enable the external OpenSSH option. The bundled version of OpenSSH will be uninstalled automatically. If you do not rely on an external OpenSSH installation, or you did not install v2.55.0(5) specifically, you can safely ignore this notice.

New Features

  • Comes with Git v2.56.0.
  • Comes with Git LFS v3.8.0.
  • Comes with cURL v8.22.0.
  • Comes with OpenSSL v3.5.8.

Bug Fixes

  • It is now finally possible to commit 4GB objects or larger in Git for Windows.
  • Fixes a bug where parallel checkouts could abort with "* stack smashing detected *: terminated".
  • A bug introduced in Git for Windows v2.55.0(5), which caused vim to often open existing files with the first line missing, was fixed.

2.103.0GitHub CLI · 21 de oct de 2026Nueva

Expiring, auto-refreshing OAuth tokens (preview)

gh can now sign in with expiring OAuth credentials that it refreshes automatically. When you opt in, gh stores a short-lived access token alongside a rotating refresh token and refreshes the access token whenever it is needed, so you stay signed in without having to authenticate again.

To opt in for a single sign-in, run:

gh auth login --expiring

To prefer expiring credentials for every sign-in, run:

gh config set expiring_credentials enabled
Ver notas completas

`gh auth status` shows whether a credential is refreshable and when the current access token expires. Both `gh auth status` and `gh auth token` automatically refresh the access token when needed. Expiring tokens are available on github.com and GHE.com; on hosts that do not issue them, `gh` falls back to a regular non-expiring token.

If you use HTTPS as your git protocol, we advise using git 2.46 or newer and letting `gh` act as your git credential helper by running `gh auth setup-git`. This way `gh` serves and refreshes the expiring credential for git, and git does not cache it past its lifetime.

> [!IMPORTANT]
> Expiring access tokens should not be cached. Scripts and extensions that store the output of `gh auth token` will eventually hold an expired token, so run `gh auth token` again each time a token is needed. Tokens supplied through `GH_TOKEN` or `GITHUB_TOKEN` are never refreshed.

For more information, see [Authenticating with GitHub CLI](https://docs.github.com/github-cli/github-cli/authenticating-with-github-cli#using-expiring-refreshable-tokens).

## Manage issue artifacts with `gh issue artifact` (private preview)

`gh issue artifact` brings issue artifacts to the command line. Users and organizations enrolled in the private preview can use the `list`, `view`, `create`, `edit`, `download`, and `delete` commands to manage issue artifacts.

Create a Markdown document with an attached image

gh issue artifact create 142 signin-plan.md --attach ./signin-flow.png

Create an HTML document

gh issue artifact create 142 menu-prototype.html

List or view artifacts

gh issue artifact list 142 gh issue artifact view 142 2

Update a document or restore an earlier version

gh issue artifact edit 142 2 --body-file signin-plan-v2.md gh issue artifact edit 142 2 --restore-version 5


Artifacts can also be addressed by their GitHub URLs, and Markdown documents support image and video attachments with `--attach`.

> [!IMPORTANT]
> Issue artifacts are in private preview. These commands only work for repositories enrolled in the preview. See the [Issue Artifacts private preview announcement and feedback discussion](https://github.com/orgs/community/discussions/205881) for access instructions and to share feedback.

2.102.0GitHub CLI · 29 de sept de 2026Nueva

Security

Four security vulnerabilities have been identified, and fixed, in this release. Users are advised to update gh to version v2.102.0 as soon as possible.

gh release download, gh run download, gh repo read-file --output, and gh attestation download could write remote content to an unintended local file when the destination contained symbolic links.

See https://github.com/cli/cli/security/advisories/GHSA-39wj-f2f4-978v for more information.

gh attestation verify compared the --source-ref value case-insensitively, so an attestation built from a branch whose name differs only in case could satisfy a policy that named a different branch.

See https://github.com/cli/cli/security/advisories/GHSA-4mq3-hpgx-9cx8 for more information.

Interactive gh skill search passed repository paths from search results to gh skill install without an option separator, so a search result could inject installer options and change where skill files were written.

Ver notas completas

See https://github.com/cli/cli/security/advisories/GHSA-qcwj-mr2r-2cx7 for more information.

gh attestation verify matched the --signer-workflow value against only the start of the signing certificate's identity, so an attestation signed by a different workflow in the pinned repository could pass verification when its path began with the pinned value.

See https://github.com/cli/cli/security/advisories/GHSA-wjmr-j3rp-mh2g for more information.

1.1Consulta y comparación de cambios

Ver cambios sin confirmar en el working directory

git diff

Compara el estado actual de tus archivos contra el último commit registrado. Muestra línea por línea qué fue agregado (en verde con +) y qué fue eliminado (en rojo con -). Es el primer comando que debes ejecutar cuando quieres revisar qué has cambiado antes de hacer un commit.

1.2Consulta y comparación de cambios

Ver archivos modificados en el último commit

git diff --name-only HEAD~1 HEAD

Muestra solo los nombres de los archivos que cambiaron en el commit más reciente, sin mostrar el contenido de los cambios. HEAD apunta al commit actual y HEAD~1 es el commit inmediatamente anterior. Útil cuando necesitas saber rápidamente qué archivos tocó el último commit.

1.3Consulta y comparación de cambios

Ver archivos diferentes entre dos ramas

git diff --name-only <rama-base>..<release>

Compara dos ramas y lista los archivos que son diferentes entre ellas. Los dos puntos .. le indican a Git que compare el estado final de ambas ramas. Útil para saber qué cambios tiene una rama de release respecto a la rama base antes de hacer un merge o despliegue.

1.4Consulta y comparación de cambios

Comparar tu rama de trabajo contra la rama base

git diff <rama-base>...<mi-rama> --name-only

Lista todos los archivos que modificaste en tu rama respecto a la rama base. Los tres puntos ... le indican a Git que busque el punto en común entre ambas ramas y compare desde ahí, ignorando cambios que ya existían en la base. Ideal para revisar exactamente qué archivos son parte de tu trabajo antes de abrir un Pull Request.

1.5Consulta y comparación de cambios

Ver archivos modificados en los últimos <N> commits

git diff --name-only HEAD~<N>..HEAD

Acumula todos los archivos que cambiaron en los últimos <N> commits y los lista. HEAD~<N> retrocede N posiciones desde el commit actual.

# Ejemplo: ver archivos de los últimos 6 commits
git diff --name-only HEAD~6..HEAD
1.6Consulta y comparación de cambios

Ver archivos modificados en el último día en una rama

git diff --name-only $(git rev-list -n 1 --before="1 days ago" <release>)..<release>

Primero ejecuta el comando interno git rev-list para encontrar cuál era el último commit de la rama hace exactamente 24 horas, y luego compara ese punto contra el estado actual. El resultado es la lista de archivos que cambiaron durante ese período. Muy útil para revisar qué se subió a producción en el día.

1.7Consulta y comparación de cambios

Ver el historial completo de un archivo (incluyendo renombrados)

git log --follow -- <archivo>

Muestra todos los commits que tocaron ese archivo específico. El flag --follow hace que Git rastree el archivo incluso si fue renombrado o movido de carpeta. Sin --follow, el historial se corta en el punto donde el archivo cambió de nombre. Los dos guiones -- le indican a Git que lo que sigue es una ruta de archivo, no una rama.

# Ver los cambios exactos (diff) de cada commit que tocó el archivo
git log --follow -p -- <archivo>

# Ver el historial en formato compacto: hash corto + mensaje
git log --follow --oneline -- <archivo>
1.8Consulta y comparación de cambios

Comparar un commit específico contra su commit padre

git diff <commit-hash>^ <commit-hash> --name-only

Muestra exactamente qué archivos se modificaron en ese commit en particular. El símbolo ^ significa "el commit anterior a este". Útil cuando alguien te comparte un hash y quieres saber qué tocó sin revisar toda la historia.

Todos los comandos de esta sección usan rsync -R que preserva la estructura de carpetas del proyecto al copiar. Si un archivo está en src/components/Button.js, llegará al destino como <destino>/src/components/Button.js.

2.1Copia de archivos modificados

Copiar archivos que difieren entre tu rama y la base

for name in $(git diff <rama-base>...<mi-rama> --name-only); do
  rsync -R "$name" "<destino>"
done

Obtiene la lista de archivos modificados entre tu rama y la base, y los copia uno a uno al destino manteniendo la estructura de carpetas. El bucle for itera sobre cada archivo de la lista y rsync -R lo copia respetando su ruta relativa.

2.2Copia de archivos modificados

Copiar archivos modificados en el último commit

for name in $(git diff --name-only HEAD~1..HEAD); do
  rsync -R "$name" "<destino>"
done

Toma exactamente los archivos que cambiaron en el último commit y los copia al destino. Útil para despliegues manuales donde solo necesitas enviar lo que cambió más recientemente.

2.3Copia de archivos modificados

Copiar archivos modificados en los últimos <N> commits (sin duplicados)

for name in $(git diff --name-only HEAD~<N>..HEAD | sort -u); do
  rsync -R "$name" "<destino>"
done

Igual que el anterior pero acumulando N commits. El pipe hacia sort -u elimina duplicados: si un mismo archivo fue modificado en varios commits, solo se copiará una vez en su versión más reciente.

2.4Copia de archivos modificados

Copiar archivos modificados en las últimas <N> horas

for name in $(git diff HEAD "@{<N>.hours.ago}" --name-only); do
  rsync -R "$name" "<destino>"
done

Filtra por tiempo en lugar de por commits. @{N.hours.ago} es una sintaxis especial de Git para referirse al estado del repositorio hace N horas. Útil cuando trabajas por bloques de tiempo.

2.5Copia de archivos modificados

Copiar archivos agregados o modificados desde medianoche

for name in $(git log --since="midnight" --pretty=format: --name-only --diff-filter=AM <rama-base>); do
  rsync -R "$name" "<destino>"
done

Filtra por fecha desde las 00:00 hrs del día actual. El flag --diff-filter=AM restringe los resultados solo a archivos Agregados y Modificados, excluyendo los eliminados para no intentar copiar archivos que ya no existen. --pretty=format: elimina encabezados de commits dejando solo los nombres de archivos.

3.1Flujo de trabajo con ramas

Buenas prácticas antes de crear una rama

# Paso 1: Actualizar las ramas base
git checkout <rama-base> && git pull
git checkout development && git pull

# Paso 2: Crear tu rama de trabajo desde la base actualizada
git checkout -b <mi-rama>

¿Por qué es importante? Si creas tu rama desde un estado desactualizado, acumularás conflictos que tendrás que resolver más adelante. Siempre hacer pull antes de ramificar garantiza que partes del código más reciente del equipo.

3.2Flujo de trabajo con ramas

Ver todas las ramas (locales y remotas)

# Solo ramas locales
git branch

# Ramas locales y remotas
git branch -a

# Solo ramas remotas
git branch -r

Lista las ramas disponibles. La rama activa aparece marcada con *. Con -a también verás las ramas que existen en el servidor remoto aunque no las tengas descargadas localmente.

3.3Flujo de trabajo con ramas

Cambiar de rama

git checkout <mi-rama>

# Forma moderna (Git 2.23+)
git switch <mi-rama>

Cambia tu working directory al estado de la rama indicada. Si tienes cambios sin confirmar, Git te pedirá que los guardes o confirmes antes de cambiar.

3.4Flujo de trabajo con ramas

Eliminar una rama

# Eliminar rama local (solo si ya fue mergeada)
git branch -d <mi-rama>

# Forzar eliminación local (aunque no haya sido mergeada)
git branch -D <mi-rama>

# Eliminar rama del servidor remoto
git push origin --delete <mi-rama>

Limpia ramas que ya no se necesitan. -d es seguro porque falla si la rama tiene trabajo sin mergear. -D lo fuerza sin verificar. Eliminar la rama remota no borra la local ni viceversa, son operaciones independientes.

3.5Flujo de trabajo con ramas

Actualizar rama local cuando hay cambios remotos pendientes

git pull --rebase --autostash
git push

Cuando alguien más subió cambios a tu misma rama y Git te impide hacer push, este comando resuelve el problema. --rebase reorganiza tus commits locales encima de los remotos en lugar de crear un merge commit innecesario. --autostash guarda automáticamente cualquier trabajo no commiteado, aplica el rebase y lo restaura al final.

3.6Flujo de trabajo con ramas

Forzar un push de forma segura

git push --force-with-lease

Fuerza el push pero con una verificación de seguridad: solo lo permite si nadie más subió cambios a esa rama desde tu último pull. Si alguien subió algo, el comando falla y te avisa, protegiendo el trabajo de tus compañeros. Es la alternativa segura a --force.

El stash es como una "caja de guardado temporal". Te permite dejar tus cambios en pausa sin hacer un commit, cambiar de tarea o de rama, y luego retomar exactamente donde lo dejaste.

4.1Stash

Guardar cambios en el stash

# Guardar con nombre descriptivo (recomendado)
git stash push -m "<mensaje>"

# Guardar rápido sin nombre
git stash

Toma todos los cambios que tienes en tu working directory (modificados y en staging), los guarda en una pila temporal y deja tu rama limpia como estaba en el último commit. Útil cuando necesitas cambiar de rama de urgencia sin haber terminado tu tarea.

4.2Stash

Ver la lista de stashes guardados

git stash list

Muestra todos los stashes guardados con su índice (stash@{0}, stash@{1}, etc.), la rama donde fueron creados y el mensaje descriptivo. El índice 0 es siempre el más reciente.

4.3Stash

Recuperar el último stash guardado

# Aplicar y eliminar el stash de la lista
git stash pop

# Aplicar sin eliminar (por si quieres aplicarlo en varias ramas)
git stash apply

Restaura los cambios guardados en tu working directory. pop los elimina de la pila al aplicarlos. apply los mantiene en la lista para poder reutilizarlos.

4.4Stash

Recuperar un stash específico

git stash pop stash@{<N>}
git stash apply stash@{<N>}

Aplica un stash específico de la lista en lugar del más reciente. El número <N> corresponde al índice que muestra git stash list.

4.5Stash

Eliminar un stash

# Eliminar un stash específico
git stash drop stash@{<N>}

# Limpiar todos los stashes
git stash clear

Elimina stashes que ya no necesitas para mantener la lista ordenada. clear borra todos de golpe, así que úsalo con precaución.

5.1Deshacer y corregir cambios

Corregir el último commit (mensaje o contenido)

# Corregir solo el mensaje del último commit
git commit --amend -m "<mensaje>"

# Agregar archivos olvidados al último commit (sin cambiar el mensaje)
git add <archivo>
git commit --amend --no-edit

Reescribe el último commit. Útil cuando cometiste un error en el mensaje o te olvidaste de agregar un archivo. Importante: solo úsalo si aún no has hecho push, porque cambia el historial y causará conflictos si otros ya tienen ese commit.

5.2Deshacer y corregir cambios

Sacar un archivo del staging area (sin perder cambios)

git restore --staged <archivo>

Si hiciste git add por error, este comando saca el archivo del staging area pero mantiene tus cambios en el working directory. Es como deshacer el git add sin perder tu trabajo.

5.3Deshacer y corregir cambios

Descartar cambios de un archivo (volver al último commit)

git restore <archivo>

Descarta todos los cambios sin confirmar de un archivo y lo vuelve exactamente al estado del último commit. ⚠️ Esta operación es irreversible: los cambios descartados no se pueden recuperar.

5.4Deshacer y corregir cambios

Revertir un commit de forma segura

git revert <commit-hash>

Crea un nuevo commit que deshace los cambios del commit indicado, sin borrar el historial. Es la forma segura de deshacer trabajo que ya fue subido al repositorio remoto, porque no reescribe el historial sino que agrega uno nuevo. Ideal para deshacer cambios en ramas compartidas o en producción.

5.5Deshacer y corregir cambios

Deshacer commits con git reset

# Deshacer commits pero conservar los cambios en staging
git reset --soft HEAD~<N>

# Deshacer commits y sacar los cambios del staging (conserva archivos)
git reset --mixed HEAD~<N>

# Deshacer commits y eliminar todos los cambios (⚠️ irreversible)
git reset --hard HEAD~<N>

Mueve el puntero HEAD N commits hacia atrás. La diferencia está en qué pasa con tus archivos:

  • --soft: los cambios quedan listos para commitear de nuevo (en staging).
  • --mixed: los cambios quedan en tu working directory pero no en staging.
  • --hard: borra todo, los archivos quedan exactamente como estaban en ese commit. ⚠️ Solo úsalo en ramas locales que no hayas compartido.
6.1Cherry-pick

Aplicar un commit específico en tu rama actual

git cherry-pick <commit-hash>

Toma los cambios de un commit específico (de cualquier rama) y los aplica como un nuevo commit en tu rama actual. Útil cuando necesitas pasar un fix puntual de una rama a otra sin hacer un merge completo. Por ejemplo, si un bug fue corregido en development y necesitas ese fix urgente en release sin mezclar todo lo demás.

6.2Cherry-pick

Aplicar varios commits en orden

git cherry-pick <commit-hash-1> <commit-hash-2> <commit-hash-3>

Aplica varios commits en el orden indicado. Es importante mantener el orden cronológico para evitar conflictos.

6.3Cherry-pick

Cherry-pick sin crear commit automáticamente

git cherry-pick <commit-hash> --no-commit

Aplica los cambios del commit en tu working directory pero no crea el commit automáticamente. Te da la oportunidad de revisar o modificar los cambios antes de confirmarlos. Útil cuando quieres combinar cambios de varios cherry-picks en un solo commit.

6.4Cherry-pick

Continuar o abortar un cherry-pick con conflictos

# Después de resolver los conflictos manualmente
git cherry-pick --continue

# Cancelar el cherry-pick y volver al estado anterior
git cherry-pick --abort
7.1Blame

Ver quién escribió cada línea de un archivo

git blame <archivo>

Muestra el archivo línea por línea con información adicional al lado: el hash del commit, el autor y la fecha en que esa línea fue escrita o modificada por última vez. Útil para entender el contexto de un cambio o encontrar quién introdujo un bug específico.

7.2Blame

Ver blame de un rango de líneas específico

git blame -L <linea-inicio>,<linea-fin> <archivo>

# Ejemplo: ver solo las líneas 20 a 35
git blame -L 20,35 <archivo>

Limita el resultado a un rango de líneas. Útil cuando tienes archivos grandes y solo te interesa una sección particular.

7.3Blame

Ver blame ignorando cambios de espaciado

git blame -w <archivo>

Ignora commits que solo cambiaron espacios o indentación, mostrando el autor del contenido real. Evita que una reindentación masiva aparezca como el "autor" de todo el archivo.

Esta es una de las confusiones más comunes en Git. Ambos traen información del servidor remoto, pero actúan de manera muy diferente.

8.1Fetch vs Pull

git fetch — Descargar sin aplicar

git fetch origin

# Ver qué cambió después del fetch
git diff HEAD origin/<mi-rama>

Descarga todos los cambios del servidor remoto y los guarda localmente, pero no modifica tu rama actual ni tu working directory. Te permite revisar qué cambió el equipo antes de decidir si integras esos cambios. Es la opción más segura cuando quieres mantenerte informado sin alterar tu trabajo.

8.2Fetch vs Pull

git pull — Descargar y aplicar

git pull origin <mi-rama>

Es equivalente a hacer git fetch seguido de git merge. Descarga los cambios del servidor y los integra inmediatamente a tu rama actual. Puede generar conflictos si tu rama y la remota divergieron.

El reflog es el "historial de todo". Registra cada movimiento de HEAD, incluyendo resets, rebases, merges y cambios de rama. Es tu red de seguridad cuando algo sale muy mal.

9.1Reflog

Ver el historial completo de movimientos

git reflog

Muestra una lista cronológica de todo lo que ha pasado en tu repositorio local: cada commit, reset, merge, rebase o cambio de rama. Cada entrada tiene un índice como HEAD@{0}, HEAD@{1}, etc. A diferencia de git log, el reflog incluye incluso commits que fueron "borrados" con git reset --hard.

9.2Reflog

Recuperar commits perdidos después de un reset --hard

# 1. Encontrar el hash del commit que perdiste
git reflog

# 2. Volver a ese punto
git reset --hard <commit-hash>

# O crear una nueva rama desde ese punto
git checkout -b <mi-rama-recuperada> <commit-hash>

Aunque hayas hecho git reset --hard, los commits no se borran inmediatamente del repositorio. El reflog los registra y puedes recuperarlos usando su hash. Es el salvavidas definitivo ante un error grave.

9.3Reflog

Ver el reflog de una rama específica

git reflog show <mi-rama>

Filtra el reflog mostrando solo los movimientos que afectaron a esa rama en particular.

Los conflictos ocurren cuando dos personas modificaron la misma parte de un archivo en ramas diferentes. Git no puede decidir cuál versión es la correcta, así que te pide que lo hagas tú.

10.1Resolución de conflictos

¿Cómo se ve un conflicto?

Cuando hay un conflicto, Git marca el archivo así:

<<<<<<< HEAD
  // Tu versión del código
=======
  // Versión del código de la otra rama
>>>>>>> <rama-origen>
  • Todo entre <<<<<<< HEAD y ======= es tu código.
  • Todo entre ======= y >>>>>>> es el código entrante.
10.2Resolución de conflictos

Flujo para resolver un conflicto

# Paso 1: Ver qué archivos tienen conflictos
git status

# Paso 2: Abrir cada archivo conflictivo, elegir qué código conservar
# y eliminar manualmente los marcadores <<<<<<<, =======, >>>>>>>

# Paso 3: Marcar el conflicto como resuelto
git add <archivo>

# Paso 4: Finalizar el merge
git commit
10.3Resolución de conflictos

Abortar el merge y volver al estado anterior

git merge --abort

Cancela el merge en curso y devuelve tu rama al estado exacto anterior al intento de merge. Útil cuando los conflictos son demasiados o necesitas más tiempo para revisarlos.

10.4Resolución de conflictos

Usar la versión de tu rama (ignorar los cambios entrantes)

git checkout --ours <archivo>
git add <archivo>
10.5Resolución de conflictos

Usar la versión de la rama entrante (ignorar tus cambios)

git checkout --theirs <archivo>
git add <archivo>

¿Qué hacen? En lugar de mezclar manualmente, estas opciones te permiten elegir una versión completa del archivo: --ours mantiene tu versión y --theirs acepta la versión que viene del merge.

El archivo .gitignore le dice a Git qué archivos o carpetas debe ignorar completamente, como dependencias instaladas, archivos de configuración local o archivos generados automáticamente.

11.1.gitignore

Crear o editar el .gitignore

Crea un archivo llamado .gitignore en la raíz de tu proyecto y agrega los patrones de lo que quieres ignorar:

# Dependencias
node_modules/
vendor/

# Archivos de entorno y configuración local
.env
.env.local
.env.*.local

# Archivos generados por el sistema operativo
.DS_Store
Thumbs.db

# Carpetas de compilación o build
dist/
build/
*.min.js

# Logs
*.log
logs/

# IDEs y editores
.vscode/
.idea/
*.sublime-workspace
11.2.gitignore

Dejar de rastrear un archivo que ya fue commiteado

# Paso 1: Agregar el archivo a .gitignore
echo "<archivo>" >> .gitignore

# Paso 2: Eliminarlo del índice de Git (sin borrarlo de tu disco)
git rm --cached <archivo>

# Paso 3: Confirmar el cambio
git commit -m "chore: remove <archivo> from tracking"

Si accidentalmente commiteaste un archivo que debería estar ignorado (como un .env), este flujo lo elimina del control de versiones sin borrarlo de tu computadora.

11.3.gitignore

Ver qué archivos están siendo ignorados

git status --ignored

Muestra todos los archivos que Git está ignorando según las reglas del .gitignore. Útil para verificar que tus reglas están funcionando correctamente.

12.1AWS S3

Ver buckets disponibles

aws s3 ls

Lista todos los buckets S3 a los que tiene acceso el perfil AWS configurado en tu máquina. Es el punto de partida para saber con qué entornos puedes trabajar.

12.2AWS S3

Listar contenido de un bucket

aws s3 ls <bucket>

Muestra los archivos y carpetas dentro del bucket, similar al comando ls en terminal. Útil para verificar el estado actual antes de sincronizar.

12.3AWS S3

Simular una sincronización (dry run — sin cambios reales)

aws s3 sync "<carpeta-local>" <bucket> --dryrun

Ejecuta toda la lógica de sincronización pero sin aplicar ningún cambio real. Muestra exactamente qué archivos se subirían, actualizarían o eliminarían. Siempre ejecuta esto primero antes de una sincronización real para evitar subidas accidentales.

12.4AWS S3

Sincronizar carpeta local hacia S3

aws s3 sync "<carpeta-local>" <bucket> --exact-timestamps

Compara los archivos locales con los del bucket y sube únicamente los que son nuevos o fueron modificados. El flag --exact-timestamps usa la fecha de modificación exacta para determinar si un archivo cambió, lo que es más preciso que comparar solo por tamaño.

12.5AWS S3

Sincronizar eliminando archivos sobrantes en S3

aws s3 sync "<carpeta-local>" <bucket> --delete --exact-timestamps

Igual que la sincronización normal, pero además elimina del bucket cualquier archivo que no exista en tu carpeta local. Deja el bucket como un espejo exacto de tu carpeta.

⚠️ Precaución: Si tienes archivos en S3 que no están localmente (backups, archivos generados por otros procesos), este comando los eliminará permanentemente. Usa --dryrun antes para revisar qué se borrará.

12.6AWS S3

Subir un archivo puntual

aws s3 cp <archivo> <bucket>/<archivo>

Copia un único archivo desde tu máquina hacia una ruta específica dentro del bucket. A diferencia de sync, no compara ni verifica nada, simplemente sube ese archivo. Útil para actualizaciones urgentes de un solo archivo.

12.7AWS S3

Descargar contenido de un bucket a local

aws s3 sync <bucket> <carpeta-local>

Invierte la dirección de la sincronización: descarga los archivos del bucket hacia tu máquina. Útil para hacer backups locales o para restaurar archivos que solo existen en S3.

12.8AWS S3

Eliminar un archivo del bucket

aws s3 rm <bucket>/<archivo>

Elimina permanentemente un archivo específico del bucket. No hay confirmación ni papelera de reciclaje, debes estar seguro de la ruta antes de ejecutarlo.

12.9AWS S3

Eliminar una carpeta completa del bucket

aws s3 rm <bucket>/<carpeta> --recursive

Elimina una carpeta y todo su contenido dentro del bucket. El flag --recursive es obligatorio para operar sobre directorios; sin él, el comando no tendrá efecto.

12.10AWS S3

Validar identidad AWS activa

aws sts get-caller-identity

Consulta al servicio de AWS cuál es la identidad que está usando tu terminal en este momento. Devuelve el ID de cuenta, el nombre de usuario o rol, y el ARN completo. Es el primer comando a ejecutar si tienes dudas sobre con qué cuenta o entorno (dev, staging, producción) estás trabajando.
